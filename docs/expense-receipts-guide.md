# Private expense receipt files

Open the actual expense in **Work expenses / Finance & expenses**, then choose **Load expense receipts** under **Private expense receipt files**. This register supports ordinary expense records, including activity-linked TADA claims. Loan/advance, cash-movement, vendor-payment and vendor-bill files use the separate deployed workflows in [Finance evidence files](finance-evidence-files-guide.md). Existing text evidence references stay supported; a file is optional, not a newly imposed approval policy.

The actual expense author may upload on a current Draft/Rejected expense within their existing work scope. Accounts/admin retain their existing draft-edit authority. A project manager's existing expense read access permits viewing registered receipts but does not grant another author's edit or expense approval powers. Clients, unrelated staff, disabled accounts and revoked scopes do not gain access. This register does not copy activity or training attachments or change expense classification, financial amounts, reviewers or payment rules.

Choose an actual PDF, PNG, JPEG or WebP file and enter an actual upload reason. These are technical limits: 10 MB per file, 10 active receipts and 20 registered files including excluded history. Basic file signatures and MIME/extension agreement are checked before upload. The upload is private, uses a new expense/file path and never overwrites existing bytes. An unchanged uncertain request reuses its request and uploaded object. If an upload succeeded but attachment is uncertain, refresh to reconcile it before changing file/reason; use **Discard unregistered receipt upload** only for your unregistered upload. Registered files are never deleted by that cleanup, including excluded files. Keep the same file/reason for an unchanged retry; new selections remain manual.

A registered receipt records the actual filename, size/MIME/private path, uploader, server time and reason. Use **Exclude receipt** with a reason to remove it from the active expense evidence; the original bytes and history remain. **Restore receipt** explicitly restores an excluded intact file within active capacity. Both operations require a current editable expense version and preserve immutable event snapshots. They advance the expense version, so stale review/actions are rejected. Submitted/Approved receipts cannot be edited; use the existing independent expense rejection/correction workflow before changing active proof.

At expense submission and approval, the actual expense financial record, active file IDs and original metadata are frozen in private immutable receipt history with the actual actor/server time. Missing/changed active object metadata blocks those transitions. Reference-only expenses continue through the existing workflow with an explicit empty file basis. No historical file approval is backfilled and no file is made mandatory for legacy expenses. Ordinary loan approval and all cash/payment rules remain unchanged.

Use private download buttons for accessible registered files, including excluded history. Owner/size/MIME metadata mismatch disables download/restore and flags the original retained evidence; this is not cryptographic verification of stored file content. Client-side content hashing is used only to distinguish upload retries and compare an already-uploaded object after a collision. It is not a server-certified receipt hash or proof that a business receipt is genuine.

**Export private expense receipt register CSV** contains only the current expense's accessible file metadata and immutable action/submission/approval history. Reasons and text are escaped for spreadsheets. Failed reads, scope changes and late responses must not restore stale private views or start a late download. No signed public links, external delivery or payment are initiated. Client-owned signed-in role/workflow/private download/export/device acceptance remains pending; no production business fixture or actual receipt was supplied by development.
