# Private client charter copy drafts

In the project charter register, an active administrator or assigned project manager chooses New client charter copy draft and selects an actual Reviewed charter. Manually enter client-facing title, objectives, scope, deliverables and communication wording plus an actual revision reason. All wording starts blank. Private source stakeholders and review notes are not automatically included.

The private draft freezes the exact source charter. Revise client charter copy keeps source/project identity, requires a new reason and explicitly captures the displayed current Reviewed source version. Refresh after source/version changes. An Archived/Draft source cannot support new saves. Earlier exact unchanged requests can be retried safely without reverting later revisions.

The copy and history exports are private and include full internal source provenance, actual actors/times/reasons and immutable revisions. They are intended for authorized internal users. Clients cannot read these tables or exports.

Draft preparation and review stay separate from publication. Administrator review/return is separate from client publication/withdrawal and client sign-off. Designated project contacts can approve the exact published version and obtain saved locked PDF evidence. Draft saving and internal review do not approve contractual scope, alter budgets, assign signers, deliver messages or give clients access. Actual business wording is supplied by authorized users.


## Internal copy review

An active administrator opens Review this client charter copy version or Return this client charter copy version and supplies the actual reason. Review requires exact current Reviewed source evidence captured in the copy; refresh and explicitly revise a stale copy first. Return can record corrections after source changes/archive. Later copy versions need new review; previous review/source evidence remains immutable. Assigned managers can inspect the scoped review archive and private CSV without administrator decision controls. Review does not publish or obtain client sign-off.


## Publication and withdrawal

An active administrator confirms the displayed actual project client company, then selects Publish reviewed charter version and enters an actual publication reason. The exact latest Reviewed copy and unchanged Reviewed source are required. Only manually authored client-facing charter fields and version/change-order metadata enter the fixed client copy, alongside publication/project/client identifiers, names and status/times. Check all manual wording for client suitability. Private source/review/actor/reason archives remain separate administrator evidence.

Clients read/export Published client charters from My contract documents (Contract documents for administrators). Withdraw open charter publication requires the exact publication version and a new manual reason; withdrawn copies stay historical and cannot be republished as the same copy version. Explicitly review a newer manual copy version to publish again after withdrawal. Later private edits/source archive never silently rewrite client wording. A current client-company membership is required; changing companies revokes old-company visibility.

Publication does not obtain client acceptance or change operative scope/budget. Designated project contacts can approve the exact published version and obtain saved locked PDF evidence. No email/SMS/WhatsApp is sent.


Authorized signatories (development increment): In Project charter and communication plan, choose the actual project under Project charter authorized signatories. The client contact selector lists only active contacts of that project's client company. Select an actual contact and enter a manual reason to grant authority. Multiple contacts may be designated. Revoke authority or restore it explicitly with a new reason; earlier decisions remain in private CSV/history. Disabled/moved contacts lose operative eligibility immediately and can still be revoked. No contact is preselected. Only active administrators/assigned PMs administer these records. Designated clients can approve the published version; each approval has saved locked PDF evidence.

Confirmed approval requirements: only designated contacts may approve the exact published client-visible scope, product lines, deliverables, milestones/dates, value, payment milestones and responsibilities; internal tasks/costs/margins stay private. Changes require a new change-order version and fresh approval. Approval requires I agree, actual typed full name and optional note, authenticated account/server time/trusted request IP, plus an immutable stamped locked PDF saved in the project. Existing three-party handover sign-off is separate. Historical five-field copies remain explicitly incomplete for approval; new copies require the expanded manual fields.


Expanded manual approval wording: Enter actual product lines, milestones/dates, contract value including currency, payment milestones and responsibilities alongside the existing client wording. Every field starts blank and is required. Select Original only for a project's first publication, with no predecessor/change summary. For later publication select Change order, select the actual latest published charter and enter an actual change summary. The administrator must explicitly withdraw previous open project publication(s), review the exact updated copy/source, then publish the new change-order version. New copy identities do not bypass this project version rule. This records client-visible charter versions only; contractual/budget changes retain their separate workflows.

Clients can read/export all frozen expanded terms and predecessor/version metadata. Legacy five-field publications remain unchanged and explicitly show that expanded approval fields were not recorded. No amounts/dates/terms are imported from internal tasks/costs/margins. Review manual wording for suitability before publication. Portal approval and locked PDF evidence are available; a published Change order never carries prior approval automatically.


Portal approval: A designated active client sees an approval form under the latest expanded Published charter. Read the fixed terms, type your actual full name, optionally add a note, and explicitly tick I agree. No name/note/agreement is prefilled. Confirm to record the exact published snapshot with your verified account, server time and platform request IP. An unchanged failed request can be retried without duplicate proof; changing the text starts a new request. Refresh if authority/version changed. Other clients can still view the charter without approving. Each designated account may record its own approval; this does not impose an all-signers rule.

Your immutable receipt and private CSV show actual account/name/time/IP/note and approved public wording. Administrators/assigned PMs can inspect their project evidence; clients receive only their own approval records. Withdrawal or change orders preserve old proof and never carry it forward. The server automatically generates a locked PDF copy and retains it in the project. If generation fails, retry Generate approval PDF; the approval is already saved. Existing handover remains separate.

Server setup: production Vercel runtime requires CHARTER_APPROVAL_GATEWAY_TOKEN (sensitive/server-only), existing VITE_SUPABASE_URL/VITE_SUPABASE_ANON_KEY and platform VERCEL=1. Private portal_private.charter_approval_gateway stores only the token SHA-256 hash, with no browser grants. Missing configuration/trusted platform IP rejects approvals. Production token is not assigned to previews. Never log or put the token in VITE_* variables/repository. Rotation must coordinate private hash replacement and a new production deployment; keep business signatory assignments manual.


Locked approval PDF: After approving, the system generates a static stamped PDF containing exactly your approved client wording/version/predecessor plus actual name/account/time/IP/agreement/note. It is saved once in the project with its SHA-256 and approval hash. Download locked approval PDF requires current project/account access and verifies original bytes. Administrators/assigned PMs can use Project charter approval documents in the charter register. Client My contract documents exposes only own approval evidence. Withdrawals/change orders keep previous approval documents unchanged; new versions need new approval.

If PDF not saved yet appears, select Generate approval PDF. A failed download/generation leaves the original approval and archive unchanged and can be retried. Standard-reader PDF permissions restrict editing/annotations; retained originals cannot be replaced/deleted through portal roles. The saved hash verifies downloaded bytes. Unsupported font glyphs retain a pending/error state rather than create blank text. Tested scripts include Latin, Greek, Cyrillic, Arabic and Urdu. The bundled fonts and license notices are packaged with the Node functions; no external font download occurs at request time.
